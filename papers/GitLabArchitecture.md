# Архитектура GitLab

> Конспект на русском по статье [GitLab Architecture: A Complete Guide](https://devopscube.com/gitlab-architecture/) (Bibin Wilson, DevOpsCube). Это пересказ, а не перевод — подробности в оригинале. Схема подгружается с сайта DevOpsCube. Раздел «Шпаргалка» в конце — дополнение по документации GitLab (Omnibus-установка), а не часть статьи.

## Что такое GitLab

GitLab — DevOps-платформа, которая закрывает весь цикл разработки в одном месте вместо набора отдельных инструментов. Её используют, например, Agoda, Airbus, CERN, Goldman Sachs и NVIDIA.

| Возможность | Что даёт |
|---|---|
| Git-репозитории | хостинг и управление кодом, как в GitHub |
| CI/CD | пайплайны, описанные в YAML |
| Задачи | планирование работ, баги, запросы на функции |
| Code review | merge request с согласованиями |
| Container Registry | хранение Docker-образов |
| Безопасность | встроенные сканеры уязвимостей |

Коротко: GitLab = хостинг кода + CI/CD + задачи + DevOps-инструменты.

## Как проходит запрос

![Архитектура GitLab](https://storage.ghost.io/c/5f/2f/5f2f4d20-2abf-4534-8d40-7aa233aedd43/content/images/2025/10/image-4.png)

1. HTTP(S)-запрос пользователя приходит в **Nginx**, который работает как reverse proxy.
2. Nginx передаёт его в **Workhorse**. Тот решает: обработать запрос сам (тяжёлые загрузки и скачивания) или передать в **Puma**.
3. Puma обслуживает быстрые запросы: читает проекты, задачи и пользователей из **PostgreSQL**, кэш и сессии — из **Redis**.
4. Фоновую работу (уведомления, задачи CI/CD) Puma ставит в очередь, её выполняет **Sidekiq**: очередь в Redis, данные — в PostgreSQL и Gitaly.
5. Все Git-данные хранит **Gitaly**.
6. Git-операции по SSH идут через **GitLab Shell** напрямую к Gitaly.

## Компоненты

Понимать архитектуру нужно, чтобы диагностировать проблемы, масштабировать, обновлять и интегрировать GitLab.

### Nginx

Reverse proxy для пользовательских запросов. Также терминирует SSL/TLS — шифрует трафик между пользователем и GitLab.

### Web UI и API

Два способа работы с GitLab: интерфейс в браузере для людей и API для программ. API есть в двух вариантах — REST и GraphQL. GraphQL удобнее для сложных запросов, современных интеграций и UI.

### Puma и Rails

Ядро GitLab написано на Ruby on Rails. Puma — веб-сервер, который принимает HTTP-запросы и передаёт их в Rails. Rails построен по схеме MVC: запрос попадает в нужный контроллер, который решает, какое действие выполнить.

### Workhorse

Reverse proxy перед Puma. Берёт на себя медленные и большие запросы (крупные загрузки и скачивания), а в Puma отправляет только быстрые. Так Puma не занят долгими операциями.

### GitLab Shell

Обслуживает Git по SSH: клонирование, push и pull со стандартной аутентификацией по ключам. Само хранение и доступ к Git-данным — задача Gitaly.

### Gitaly

Сервис хранения репозиториев. Rails и GitLab Shell обращаются к нему по gRPC для всех Git-операций: push, коммиты, merge request и т.д.

### Sidekiq

Обработчик фоновых задач. Например, нужно разослать сотни писем: Rails ставит задачу в очередь Redis, а воркеры Sidekiq забирают и выполняют её. Основные запросы пользователей при этом не тормозят.

### Redis

Хранилище в памяти для временных данных:

- очередь задач Sidekiq;
- кэш часто запрашиваемых данных;
- временное состояние приложения, например статус CI/CD-джобы.

Всё долговременное лежит в PostgreSQL.

### PostgreSQL

Реляционная БД для долговременных данных: аккаунты пользователей, проекты, права, задачи, merge request, метаданные пайплайнов и реестра.

### Bare-репозитории

У каждого проекта на сервере есть bare-репозиторий — Git-репозиторий без рабочей копии файлов. Локально всё содержимое Git (коммиты, ветки, теги, история) лежит в каталоге `.git`. На сервере GitLab хранится только эта часть. Она нужна для синхронизации и базовых Git-операций (push, pull), которые обслуживают вместе Rails, GitLab Shell и Gitaly — по HTTP или SSH.

## Хранение данных

| Данные | Где хранятся |
|---|---|
| Git-репозитории | bare-репозитории на файловой системе под управлением Gitaly |
| Метаданные (пользователи, проекты, задачи, сборки CI/CD, метки) | PostgreSQL |
| Кэш и очереди | Redis (плюс кэш в памяти и HTTP-кэш) |
| Артефакты CI/CD, пакеты, вложения | лучше в объектном хранилище: AWS S3, Azure Blob, MinIO |

## Масштабирование и отказоустойчивость

Когда проект растёт, а платформенная команда предоставляет GitLab как сервис многим командам, масштабирование становится ключевым вопросом.

- Масштабировать весь GitLab целиком не обязательно — масштабируются отдельные компоненты под нагрузку.
- Stateful-компоненты с тяжёлым вводом-выводом (PostgreSQL, Redis, Gitaly) разворачивают кластерами, а не одиночными экземплярами.
- Реплики распределяют по нескольким зонам доступности.
- Регулярные бэкапы нужны для восстановления после аварий.

## Аутентификация

- По умолчанию — логин и пароль; для безопасности включите двухфакторную аутентификацию.
- В enterprise — внешние провайдеры: LDAP, SAML, OAuth2.
- Git-операции через GitLab Shell — по SSH.
- API — Personal Access Token или bearer-токен.

## Авторизация

Права выдаются пользователям и приложениям иерархически — на уровне группы или проекта.

| Роль | Права |
|---|---|
| Guest | только просмотр |
| Reporter | чтение всего и работа с задачами |
| Developer | чтение и запись |
| Maintainer | администрирование проекта, почти полный контроль |
| Owner | полный контроль |

## Мониторинг

Self-hosted GitLab мониторят через Prometheus и Grafana: внутренние метрики показывают производительность, здоровье системы и проблемы, а дашборды их визуализируют. Логи всех компонентов собраны в `/var/log/gitlab/`. Их можно отправлять коллектором (например, Fluent Bit) в централизованную систему логирования.

## Шпаргалка

### Управление Omnibus-установкой

```bash
sudo gitlab-ctl status              # состояние всех сервисов
sudo gitlab-ctl restart [сервис]    # перезапуск всех или одного (puma, sidekiq, gitaly…)
sudo gitlab-ctl reconfigure         # применить /etc/gitlab/gitlab.rb
sudo gitlab-ctl tail [сервис]       # логи в реальном времени
sudo gitlab-rake gitlab:check SANITIZE=true   # самодиагностика
sudo gitlab-rake gitlab:env:info    # версии компонентов
```

### Важные пути

| Путь | Что там |
|---|---|
| `/etc/gitlab/gitlab.rb` | основная конфигурация |
| `/etc/gitlab/gitlab-secrets.json` | ключи шифрования (обычный бэкап их **не** включает) |
| `/var/opt/gitlab/` | данные: репозитории, БД, Redis |
| `/var/opt/gitlab/backups/` | бэкапы по умолчанию |
| `/var/log/gitlab/<сервис>/` | логи по компонентам |

### Бэкап и восстановление

```bash
sudo gitlab-backup create
# отдельно сохраните конфигурацию и секреты
sudo cp /etc/gitlab/gitlab.rb /etc/gitlab/gitlab-secrets.json /безопасное/место/

# восстановление (та же версия GitLab)
sudo gitlab-ctl stop puma
sudo gitlab-ctl stop sidekiq
sudo gitlab-backup restore BACKUP=<метка_времени>
sudo gitlab-ctl reconfigure
sudo gitlab-ctl restart
```

### Где искать проблему

| Симптом | Куда смотреть |
|---|---|
| 502 / страница не открывается | `nginx`, `gitlab-workhorse`, `puma` |
| медленный UI | `puma`, PostgreSQL, Redis |
| не уходят письма, висят фоновые задачи | `sidekiq`, Redis |
| ошибки clone/push | `gitaly`, `gitlab-shell` (для SSH) |
| не стартуют пайплайны | `sidekiq`, раннеры, Redis |

### Чек-лист для продакшена

- [ ] TLS на Nginx, 2FA для пользователей, SSO через LDAP/SAML/OAuth2.
- [ ] Артефакты, пакеты и вложения — в объектном хранилище.
- [ ] Регулярные бэкапы, отдельный бэкап `gitlab-secrets.json` и `gitlab.rb`, проверка восстановления.
- [ ] При росте нагрузки — кластеры PostgreSQL, Redis и Gitaly в разных зонах.
- [ ] Метрики в Prometheus/Grafana, логи — в централизованную систему.
